# Audit Keamanan Menyeluruh — infarm.id (Ecommerce + OMS)
**Tanggal**: 2026-07-24 · **Sifat**: Read-only — tidak ada kode/dependency yang diubah pada sesi ini (termasuk saat menjalankan `npm audit`, tanpa `--fix`).
**Acuan**: OWASP Top 10 (2021) + kategori spesifik A–H sesuai brief audit + kerentanan umum lainnya.
**Cakupan**: Seluruh source `src/`, `supabase/migrations/`, konfigurasi root (`next.config.ts`, `package.json`, `.gitignore`), dan histori git.

> Catatan: file ini menggantikan snapshot audit RLS-fokus yang dibuat lebih awal di hari yang sama (isinya sudah dilebur & diperluas ke laporan ini).

## Metodologi

Investigasi dilakukan lewat 10 sub-audit paralel (read-only), masing-masing membaca seluruh file migration, seluruh route API relevan, komponen client/server, dan menjalankan command read-only (`npm audit`, `git log`, `git ls-files`) tanpa mengubah dependency/kode:

1. RLS Supabase & pemakaian `service_role`
2. Server Action, environment variable, hardcoded secret
3. Webhook Xendit & idempotency
4. Validasi input (no_telepon, email, harga, `.ilike`)
5. Fitur lacak/batalkan/review berbasis no_telepon (rate limit, enumeration, data exposure)
6. Upload file gambar produk, dependency, riwayat git
7. XSS, CSRF, CORS, HTTP security headers
8. IDOR & broken access control OMS (tabel lengkap endpoint × `requireAdmin`)
9. Business logic: harga, stok, promo/diskon, race condition
10. SSRF, logging/monitoring, `npm audit` sungguhan, CI/CD integrity

**Skala risiko**: **Kritis** (dieksploitasi tanpa syarat khusus, dampak besar — bypass auth, akses/tulis data/aksi milik orang lain) · **Tinggi** (dieksploitasi relatif mudah, dampak signifikan tapi cakupan lebih sempit) · **Sedang** (butuh prasyarat tertentu — mis. sesi admin sudah valid — atau dampak terbatas) · **Rendah** (hardening/best-practice, dampak kecil/kondisi langka).

## 🔴 Temuan KRITIS

### K1 — ✅ DIPERBAIKI (2026-07-24) — Tidak ada rate limiting di seluruh endpoint guest-by-phone → enumeration nomor telepon & potensi pembatalan pesanan orang lain
**Kategori**: F (Broken Access Control OMS-adjacent) / B (Auth Failures) — OWASP #1 & #7
**Lokasi**: `src/app/api/orders/track-by-phone/route.ts`, `verify-cancel/route.ts`, `cancel-by-phone/route.ts`, `src/app/api/reviews/reviewable-by-phone/route.ts`, `create-by-phone/route.ts` (semua hanya berkomentar `TODO(rate-limit)`, tanpa implementasi)
**Deskripsi**: Berbeda dari `/api/oms/login` yang sudah punya rate limiter in-memory (5/menit per IP+username), kelima endpoint guest-by-phone ini **tidak punya mekanisme pembatas permintaan apa pun**. Nomor HP Indonesia punya prefix operator terbatas (0812, 0813, 0821, 0851, dst), sehingga ruang pencarian efektif jauh lebih kecil dari 10 miliar kombinasi teoretis. Tanpa rate limit, penyerang bisa mem-brute-force nomor telepon untuk: (a) menemukan nomor mana saja yang pernah belanja (enumeration — nama ter-mask, status, resi, item), dan (b) pada `cancel-by-phone`, berpotensi **membatalkan pesanan orang lain** karena satu-satunya syarat adalah kecocokan nomor telepon dengan order (tidak perlu OTP/verifikasi tambahan). Honeypot `website` hanya menghambat bot generik yang mengisi form HTML — tidak menghambat script yang menyusun request JSON langsung ke API.
**Rekomendasi**: Implementasikan rate limiting per-IP (idealnya juga per-nomor-telepon-dinormalisasi) di kelima endpoint, dengan threshold lebih ketat untuk endpoint penulis (`cancel-by-phone`, `create-by-phone`) dibanding endpoint baca (`track-by-phone`). Untuk lingkungan serverless multi-instance, in-memory Map (seperti pola `oms/login`) adalah mitigasi awal yang lebih baik daripada tidak ada sama sekali, tapi solusi jangka panjang butuh penyimpanan bersama (Supabase table/Redis).

**✅ Perbaikan yang diterapkan**: Helper rate limiter in-memory baru `src/lib/rate-limit.ts` (`isRateLimited`, `getClientIp`, pola sama dengan `/api/oms/login`), dipasang di kelima endpoint dengan **dua lapis pembatas**: (1) per-IP — menahan laju request dari satu sumber; (2) per-nomor-telepon-dinormalisasi — mencegah brute-force terdistribusi dari banyak IP ke satu nomor target. Threshold dibedakan: endpoint baca (`track-by-phone`, `verify-cancel`, `reviewable-by-phone`) 20/IP/15 menit + 15/nomor/jam; endpoint tulis/destruktif (`cancel-by-phone`, `create-by-phone`) lebih ketat, 8/IP/15 menit + 5/nomor/jam. Melebihi batas → `429` dengan pesan generik (tidak membocorkan detail). Diverifikasi lolos `npx tsc --noEmit`. **Catatan residual**: masih in-memory per-instance (bukan pengganti rate limit terpusat lintas-instance di Vercel serverless) — dicatat sebagai R2 di bagian Rendah, kandidat migrasi ke tabel Supabase/Redis.

### K2 — Secret HMAC sesi admin OMS punya fallback hardcoded di source code
**Kategori**: B (Autentikasi & Otorisasi) — OWASP #7 (Auth Failures) & #2 (Cryptographic Failures)
**Lokasi**: `src/lib/oms-auth.ts:21` — `const SECRET = process.env.OMS_SESSION_SECRET ?? 'infarm-dev-oms-session-secret'`
**Deskripsi**: Bila env var `OMS_SESSION_SECRET` lupa di-set di production, secret HMAC yang dipakai untuk menandatangani cookie sesi admin jatuh ke string default yang **tertulis jelas di source code**. Siapa pun yang membaca source (repo bocor/di-clone/open-source) dapat menghitung tanda tangan valid dan **memalsukan cookie sesi admin**, bypass login OMS sepenuhnya tanpa perlu tahu password. Ada komentar TODO di kode yang sudah mengakui risiko ini, tapi fallback belum dihapus.
**Rekomendasi**: Hapus fallback; lempar error saat startup (fail-fast) bila `OMS_SESSION_SECRET` kosong pada `NODE_ENV=production`. Pastikan env ini benar-benar di-set di Vercel sebelum deploy berikutnya.

### K3 — Halaman login OMS (Client Component) mengimpor modul yang membawa secret
**Kategori**: C (Sensitive Data Exposure) — OWASP #2
**Lokasi**: `src/app/oms/login/page.tsx:1,13` (`'use client'` di baris 1, meng-`import { sanitizeOmsRedirect } from '@/lib/oms-auth'`)
**Deskripsi**: `oms-auth.ts` yang sama juga mendefinisikan `SECRET` (K2) dan fungsi `sign()`/`createSessionToken()`/`verifySessionToken()` di top-level module scope. Project **tidak memakai package `server-only`** untuk memaksa boundary server/client secara teknis — hanya komentar tekstual. Tidak ada jaminan build-time bahwa modul pembawa secret ini tidak ikut ter-bundle ke JS yang dikirim ke browser saat Next.js membangun halaman login (tree-shaking konstanta modul-level tidak selalu bisa diandalkan).
**Rekomendasi**: Pisahkan `sanitizeOmsRedirect` (fungsi non-secret) ke modul terpisah dari `SECRET`/fungsi sign/verify, ATAU tambahkan `import 'server-only'` di `oms-auth.ts` agar build gagal eksplisit bila diimpor dari Client Component manapun.

### K4 — Password admin default (`admin123`) tersimpan di file migration yang ikut ter-commit
**Kategori**: B (Autentikasi & Otorisasi) — OWASP #7
**Lokasi**: `supabase/migrations/20260708120000_init_admin_users.sql:26-38`
**Deskripsi**: Migration men-seed akun `admin@infarm.id` dengan password default `admin123` (plus hash-nya) langsung di file SQL yang ada di repository Git. Jika password ini belum diganti di production, akun admin — dengan akses penuh manajemen produk/order/harga/stok — bisa diambil alih hanya dengan kredensial yang mudah ditebak dan terdokumentasi di source.
**Rekomendasi**: Konfirmasi password default sudah diganti di production. Untuk ke depan, hindari menaruh kredensial seed apa pun (bahkan "sementara") dalam file migration yang ikut ter-commit — gunakan proses seed terpisah di luar version control, atau paksa ganti password di first-login.

## 🟠 Temuan TINGGI

### T1 — IDOR pada `GET /api/orders/get`: tanpa auth/token/rate-limit, nama lengkap ter-expose, invoice mudah ditebak
**Kategori**: F (Broken Access Control) / C (Sensitive Data Exposure) — OWASP #1
**Lokasi**: `src/app/api/orders/get/route.ts:12-34`
**Deskripsi**: Endpoint ini (dipakai `/track?order=`, `/order-cancellation`) tidak memerlukan otentikasi/token apa pun — cukup tahu `nomor_invoice`. Response mengembalikan `customerName` **utuh, tidak di-mask** (berbeda dari `track-by-phone` yang memakai `maskName()`) beserta daftar item & status. Format invoice `INV-{YYYYMMDD}-{4 digit acak dari Math.random()}` hanya punya **~9.000 kombinasi per hari** (`generateInvoiceNumber`, `src/lib/mock-db/orders.ts:113-119`), dan tanpa rate limit di endpoint ini, seluruh ruang kombinasi 1 hari bisa di-brute-force dalam hitungan menit dari satu IP. Kontras dengan `GET /api/orders/cancel?id=&token=` yang mewajibkan token HMAC (`verifyCancelToken`) — `orders/get` sama sekali tidak memakai proteksi setara meski mengembalikan PII (nama lengkap).
**Rekomendasi**: Tambahkan minimal salah satu: (a) rate limiting per-IP, (b) mask `customerName` seperti `track-by-phone`, (c) syarat token tambahan sebelum mengembalikan nama lengkap.

### T2 — Kerentanan CVE pada `next`/`postcss`/`sharp` (termasuk 2 CVE SSRF & 1 arbitrary file read)
**Kategori**: G (Vulnerable Dependencies) — OWASP #6
**Lokasi**: `package.json` (`next: 16.2.7`)
**Deskripsi**: `npm audit` sungguhan dijalankan (read-only, tanpa fix) dan menemukan **5 kerentanan High**, seluruhnya berakar dari `next@16.2.7` (rentang rentan `>=16.0.0 <16.2.11`) beserta dependency bawaannya:
  - `postcss` — **GHSA-6g55-p6wh-862q**: arbitrary file read via `sourceMappingURL` pada komentar CSS (CVSS 7.5).
  - Next.js — **GHSA-p9j2-gv94-2wf4**: SSRF via `rewrites` dengan hostname tujuan yang dikontrol penyerang.
  - Next.js — **GHSA-89xv-2m56-2m9x**: SSRF di Server Actions pada custom server.
  - Next.js — **GHSA-955p-x3mx-jcvp**: unauthenticated disclosure endpoint Server Function internal.
  - Next.js — **GHSA-m99w-x7hq-7vfj**, **GHSA-4c39-4ccg-62r3**, **GHSA-q8wf-6r8g-63ch**, **GHSA-6gpp-xcg3-4w24**: DoS/bypass middleware terkait lainnya.
  - `sharp` (Image Optimization) — kerentanan bawaan `libvips`.

  Fix tersedia **tanpa bump major** (`next` → `16.2.11`, `fixAvailable.isSemVerMajor: false`).
**Rekomendasi**: Prioritaskan upgrade `next` ke `16.2.11` (menutup 2 CVE SSRF + arbitrary file read sekaligus), lalu jalankan `npm run build` + smoke test sebelum deploy.

### T3 — Dependency dev berisiko High (`brace-expansion`, `js-yaml`)
**Kategori**: G (Vulnerable Dependencies) — OWASP #6
**Lokasi**: `package.json` (dev dependency, transitif dari `typescript-eslint`)
**Deskripsi**: `npm audit` (output teks) menunjukkan `brace-expansion` (DoS eksponensial, GHSA-3jxr-9vmj-r5cp) dan `js-yaml` (DoS kuadratik via YAML merge-key, GHSA-52cp-r559-cp3m) — keduanya High, tapi dev-only (tidak masuk bundle production), fix tersedia via `npm audit fix` biasa (tanpa `--force`).
**Rekomendasi**: Jalankan `npm audit fix` (non-force) terpisah dari upgrade `next`.

## 🟡 Temuan SEDANG

### S1 — `discount` dari client tidak divalidasi terhadap tabel `promotions`
**Kategori**: H (Business Logic Flaws) — OWASP #4 (Insecure Design)
**Lokasi**: `src/app/api/orders/create/route.ts:97-102`
**Deskripsi**: Server hanya melakukan `Math.min(Math.round(extra.discount), subtotal)` — tidak pernah query `promotions` untuk memastikan promo `is_active`, belum `end_at`, `subtotal` mencapai `min_purchase`, atau `discount` sesuai `discount_value` yang tersimpan di DB. UI checkout saat ini **tidak mengirim** field `discount` (jadi tidak ter-eksploitasi lewat browser normal), tapi endpoint tetap menerima nilai ini bila diakses langsung (curl/Postman) — bisa dipakai mengklaim diskon hampir 100% dari subtotal tanpa promo apa pun benar-benar tercapai. Komentar kode sendiri menandai ini "wiring promo→order masih roadmap".
**Rekomendasi**: Sebelum fitur promo di-wire penuh ke order, validasi `discount` di server terhadap tabel `promotions` (status aktif, periode, `min_purchase` vs subtotal server) — jangan terima nilai nominal mentah dari client.

### S2 — Endpoint `GET /api/reviews/list` tidak dilindungi `requireAdmin()`
**Kategori**: F (Broken Access Control OMS) — OWASP #1
**Lokasi**: `src/app/api/reviews/list/route.ts:13-16`
**Deskripsi**: Endpoint ini didesain khusus untuk dashboard OMS (komentar file eksplisit menyebutnya begitu) dan memanggil `listReviewsForOms()` yang mengembalikan **seluruh** baris `reviews` tanpa filter `visible=true` — termasuk ulasan yang sudah disembunyikan moderator dan balasan admin yang belum tayang. Berbeda dari pola konsisten di endpoint OMS lain (`orders/list`, `products/*`, dll), route ini **tidak memanggil `requireAdmin()`** sama sekali — siapa pun tanpa sesi admin bisa mengaksesnya.
**Rekomendasi**: Tambahkan `requireAdmin()` di awal handler, konsisten dengan pola endpoint OMS lainnya.

### S3 — Race condition (TOCTOU) pada pembatalan pesanan → potensi stok dikembalikan dua kali
**Kategori**: H (Business Logic Flaws) — OWASP #4
**Lokasi**: `src/lib/mock-db/orders.ts` (`updateOrderStatus`, `restoreStock`), dipakai `src/app/api/orders/cancel/route.ts`, `cancel-by-phone/route.ts`, `update-status/route.ts`
**Deskripsi**: `updateOrderStatus` melakukan `UPDATE ... WHERE nomor_invoice = orderId` **tanpa syarat status lama** (bukan compare-and-swap), dan `restoreStock` melakukan read-modify-write terpisah (baca stok → tulis stok+qty) alih-alih increment atomik SQL. Dua request cancel yang tiba nyaris bersamaan (double-click, retry jaringan, dua tab) untuk order yang sama berpotensi membuat stok dikembalikan dua kali. Pola ini juga menjadi risiko bila ditiru saat membangun webhook Xendit nanti (lihat catatan Webhook di bawah).
**Rekomendasi**: Ubah `updateOrderStatus` jadi compare-and-swap (`.eq('order_status', statusLama)`), dan `restoreStock` jadi increment atomik SQL (RPC), idealnya digabung dalam satu transaksi.

### S4 — Tidak ada satu pun HTTP security header dikonfigurasi
**Kategori**: E (Security Misconfiguration) — OWASP #5
**Lokasi**: `next.config.ts` (seluruh file, konfigurasi kosong)
**Deskripsi**: Tidak ada `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Strict-Transport-Security`, `Referrer-Policy`, maupun `Permissions-Policy`. Dampak paling konkret: halaman `/oms/login` dan `/oms/dashboard/**` bisa di-iframe oleh situs lain (risiko **clickjacking** terhadap admin — mis. overlay transparan di atas form login/tombol aksi).
**Rekomendasi**: Tambahkan `headers()` di `next.config.ts` minimal `X-Frame-Options: DENY` (prioritas untuk `/oms/*`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security` (setelah HTTPS dipastikan), dan `Content-Security-Policy` (mulai report-only untuk memetakan resource eksternal yang dipakai — Google Fonts, dsb).

### S5 — Tidak ada audit log aksi admin & logging error tidak konsisten
**Kategori**: I (Logging & Monitoring Failures) — OWASP #9
**Lokasi**: Tidak ada tabel `audit_log`/sejenis di `supabase/migrations/`; hanya 2 dari puluhan route API yang memakai `console.error` (`orders/create`, `products/check-sku`)
**Deskripsi**: Tidak ada jejak "siapa mengubah apa kapan" untuk mutasi OMS (produk, order, harga, stok). Error di route lain ditangkap `try/catch` tapi tidak dicatat — hilang begitu saja. Tidak ada logging saat rate-limit login OMS terpicu, tidak ada Sentry/APM. Kombinasi ini berarti serangan (brute force login, enumeration nomor telepon) berlangsung **senyap tanpa jejak** yang bisa dipakai admin/dev untuk deteksi dini.
**Rekomendasi**: Tambah tabel `audit_log` sederhana untuk mutasi OMS; konsistenkan `console.error` di semua `catch` block (agar masuk Vercel Logs); log saat rate-limit terpicu; pertimbangkan Sentry/structured logging sebelum go-live.

### S6 — `reviewable-by-phone` membocorkan nama lengkap (tidak di-mask)
**Kategori**: C (Sensitive Data Exposure) — OWASP #2
**Lokasi**: `src/app/api/reviews/reviewable-by-phone/route.ts:22,63`
**Deskripsi**: Field `customerName` dikembalikan utuh, berbeda dari `track-by-phone` yang memakai `maskName()`. Dikombinasikan dengan K1 (tanpa rate limit), penyerang yang mem-brute-force nomor telepon lewat endpoint ini langsung memperoleh pasangan (no. telepon valid → **nama lengkap** pemiliknya) — lebih sensitif dari nama ter-mask di endpoint saudaranya.
**Rekomendasi**: Terapkan `maskName()` pada response ini, atau biarkan field nama tetap kosong dan minta user mengetik ulang secara manual (field ini memang sudah `editable` di form review).

### S7 — `orders/create` tidak validasi format `customerPhone` di server
**Kategori**: A (Injection & Input Validation) — OWASP #4
**Lokasi**: `src/app/api/orders/create/route.ts:42`
**Deskripsi**: Validasi hanya `typeof b.customerPhone === 'string'`, tidak memanggil `isValidPhone`. Client memblokir format salah, tapi endpoint publik ini bisa dipanggil langsung dengan `customerPhone` string apa pun — order tersimpan dengan `no_telepon` malformed, yang berakibat pesanan itu **tidak akan pernah bisa dilacak/dibatalkan/direview** lewat fitur by-phone (endpoint lain mewajibkan format valid).
**Rekomendasi**: Tambahkan `isValidPhone(body.customerPhone)` wajib (bukan opsional), tolak 422 bila gagal — konsisten dengan 5 endpoint by-phone lainnya.

### S8 — `products/update` tidak menjalankan ulang validator range/format
**Kategori**: A (Injection & Input Validation) — OWASP #4
**Lokasi**: `src/app/api/products/update/route.ts:34-51`
**Deskripsi**: Route ini tidak mengimpor apa pun dari `@/lib/product-validation` (berbeda dari `create/route.ts`). Akibatnya: `price` hanya dicek `>=0` (tanpa `PRICE_MAX`/`PRICE_MIN`), `stock` hanya `>=0` (tanpa `STOCK_MAX`/cek integer), `sku` tidak divalidasi format regex, `name`/`description` tanpa batas panjang, `images` tidak dicek terhadap `MAX_PRODUCT_IMAGES=9`. Membutuhkan sesi admin, jadi risiko utamanya adalah defense-in-depth yang lemah bila akun admin dikompromikan, bukan celah publik anonim.
**Rekomendasi**: Panggil ulang validator yang sama dari `product-validation.ts` seperti di `create/route.ts`.

### S9 — Server tidak validasi ulang tipe/isi/ukuran gambar produk (hanya percaya client)
**Kategori**: A (Injection & Input Validation) — OWASP #4
**Lokasi**: `src/app/api/products/create/route.ts:60-66`, `update/route.ts:53-55`, `src/lib/mock-db/products.ts:35-59`
**Deskripsi**: `MAX_IMAGE_BYTES` dan `ACCEPTED_IMAGE_TYPES` tidak pernah diimpor/dipakai di kedua route API — validasi ukuran & tipe file hanya berjalan di client. Fungsi `uploadImageIfDataUrl` mengambil `mime` mentah dari string yang diklaim client dan memakainya langsung sebagai `contentType` saat upload ke Storage publik, tanpa cross-check ke whitelist atau magic-bytes. Butuh sesi admin untuk dieksploitasi.
**Rekomendasi**: Validasi ulang MIME (whitelist + magic-bytes) dan ukuran file di server sebelum decode/upload.

### S10 — Tidak ada batas ukuran base64 sebelum decode → risiko DoS
**Kategori**: H (Business Logic/Insecure Design) — OWASP #4
**Lokasi**: `src/lib/mock-db/products.ts:43`, `src/app/api/products/{create,update}/route.ts`
**Deskripsi**: Tidak ada pengecekan panjang string base64 sebelum `Buffer.from(..., 'base64')` didekode, dan tidak ada batas ukuran body eksplisit di Route Handler. Kombinasi dengan S8/S9 (jumlah gambar tak dibatasi di `update`) membuka risiko DoS ringan (memori/bandwidth/kuota Storage) bagi aktor bersesi admin.
**Rekomendasi**: Cek estimasi ukuran dari panjang string base64 sebelum decode, tolak bila melebihi `MAX_IMAGE_BYTES`.

### S11 — `.ilike()` pada login admin rentan wildcard pattern, tanpa batas panjang
**Kategori**: A (Injection & Input Validation) — OWASP #3
**Lokasi**: `src/lib/mock-db/admins.ts:52`, `src/app/api/oms/login/route.ts:43`
**Deskripsi**: `.ilike('username', username.trim())` tanpa escape `%`/`_`. Bukan SQL injection (parameterized), tapi wildcard/pattern-matching yang tidak diinginkan pada kolom identitas login. Dampak observable saat ini terbatas (pesan error tetap generik), tapi menyimpang dari kontrak "cari exact username".
**Rekomendasi**: Ganti ke `.eq('username', ...)` atau escape `%`/`_` sebelum `.ilike()`; tambahkan batas panjang input.

### S12 — Tabel `order_items` tanpa migration eksplisit → status RLS tak terverifikasi tertulis
**Kategori**: F (Broken Access Control / RLS) — OWASP #1
**Lokasi**: `supabase/migrations/` (tidak ada file untuk `order_items`), disebut hanya di komentar `20260702120000_create_order_with_items.sql:10`
**Deskripsi**: Tabel dibuat manual di Dashboard (di luar riwayat migration). Tidak ada bukti tertulis `alter table order_items enable row level security` pernah dijalankan. Karena tabel ini berelasi ke PII (`orders`), bila RLS ternyata belum aktif secara fisik, anon key bisa membaca/menulis seluruh baris tanpa batas.
**Rekomendasi**: Verifikasi langsung di Supabase Dashboard/SQL Editor (`select relrowsecurity from pg_class where relname='order_items'`). Bila belum aktif, jalankan `alter table ... enable row level security` via migration baru (didokumentasikan, tanpa policy publik).

### S13 — CSRF: tidak ada token/origin-check eksplisit di endpoint API OMS
**Kategori**: D (CSRF & Request Forgery) — OWASP #1/#4
**Lokasi**: `src/lib/oms-guard.ts`, `src/app/api/oms/login/route.ts:76-82`, seluruh endpoint mutasi OMS
**Deskripsi**: Tidak ada Server Actions (`'use server'` — 0 hasil grep), semua mutasi lewat API Routes custom yang tidak mendapat proteksi origin-check otomatis dari Next.js. Namun kombinasi `SameSite=Lax` (cookie sesi) + `httpOnly` + keharusan `Content-Type: application/json` (memicu CORS preflight untuk request lintas origin, yang akan gagal karena tidak ada header CORS custom) membuat vektor CSRF klasik (form auto-submit) **praktis tidak berfungsi** — jadi risiko riil relatif rendah, tapi tanpa lapisan eksplisit (CSRF token/origin-check manual).
**Rekomendasi**: Naikkan `sameSite` cookie sesi OMS ke `'strict'` (OMS adalah back-office, kemungkinan tidak mengganggu UX); tambahkan pengecekan header `Origin`/`Referer` di `requireAdmin()` sebagai defense-in-depth untuk endpoint destruktif (`products/delete`, `orders/update-status`).

## Catatan Khusus: Webhook Xendit (belum diimplementasikan)

Dikonfirmasi **tidak ada** implementasi webhook Xendit di codebase saat ini (`src/lib/xendit/` dan `src/app/api/webhooks/xendit/route.ts` belum ada), sesuai roadmap di CLAUDE.md. Bukan temuan aktif, tapi wajib dipenuhi **sejak commit pertama** implementasi nanti:
1. Verifikasi signature/callback token sebelum memproses apa pun.
2. Idempotency berbasis **unique constraint DB** (bukan in-memory) atas `event_id`.
3. Tolak replay — event yang sama tidak boleh memicu efek ganda (lihat pola bug yang sama di S3).
4. Update status + efek samping dalam satu transaksi atomik (RPC), meniru pola `create_order_with_items`.

## ✅ Yang Sudah Benar (jangan diubah tanpa alasan)

- **Injection**: seluruh query Supabase terparametrisasi via query builder — tidak ada raw SQL string concat, tidak ada celah SQL injection.
- **XSS**: tidak ada `dangerouslySetInnerHTML`/`innerHTML=`/`document.write` di seluruh `src/`. Komentar/reply review dirender via JSX biasa (auto-escape React).
- **CORS**: tidak ada header CORS custom di endpoint manapun — default same-origin Next.js, postur yang benar untuk API internal.
- **Harga & stok checkout**: `orders/create` re-price setiap item dari DB (`prod.promoPrice`), mengabaikan `price` dari client sepenuhnya; validasi produk archived sebelum order dibuat; `totalAmount` dihitung ulang di server. RPC `create_order_with_items` memakai row lock (`SELECT ... FOR UPDATE`) — tidak ada race condition oversell, dan `raise exception` melakukan rollback penuh transaksi (order + items + stok).
- **Broken access control OMS**: seluruh endpoint mutasi (`products/create|update|delete`, `combos/*`, `promotions/*`, `reviews/reply|visibility`, `orders/list`, `orders/update-status`) terverifikasi memanggil `requireAdmin()` dengan pola `return` yang benar — tidak ada yang "lolos" karena lupa return (kecuali S2).
- **Fitur by-phone (kecuali rate limit)**: honeypot diverifikasi di server (bukan hanya client) pada 5 endpoint; `create-by-phone` & `cancel-by-phone` melakukan re-verifikasi kepemilikan penuh ke DB (bukan percaya client); `track-by-phone` hanya mengembalikan info non-sensitif dengan nama ter-mask.
- **Secret management**: `SUPABASE_SERVICE_ROLE_KEY` tidak pernah bocor ke bundle client (satu titik definisi, semua pemanggil server-only); `browser.ts` hanya memakai anon key; `.env*` tidak pernah ter-commit ke git di histori manapun (dikonfirmasi `git log --all --full-history`).
- **SSRF**: proxy alamat Mengantar memakai host tujuan fixed (hardcoded), hanya `keyword` sebagai query param — tidak ada celah SSRF pada kode aplikasi (CVE SSRF yang ditemukan berasal dari framework Next.js sendiri, lihat T2).
- **Path traversal upload**: nama file di Supabase Storage dibentuk server memakai `randomUUID()`, bukan nama asli dari client.
